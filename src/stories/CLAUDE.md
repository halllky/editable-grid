# ドキュメント（Storybook の mdx・デモ）執筆方針

このディレクトリのドキュメントは、人間が AI の草稿を大幅に添削して作ってきた。
以下は添削の理由を一般化した方針。個々の項目を機械的に当てはめるのではなく、
末尾の「迷ったときの問い」に照らして判断すること。

## 読み手

このグリッドを使って自分の画面を作ろうとしている開発者。
「X をしたいがこのグリッドではどうやるか」「思った通りに動かないのはなぜか」という具体的な問いを持って来る。
すべての判断は「この読み手が問いの答えに最短でたどり着けるか」で行う。

## 1. 範囲はこのコンポーネントの約束事に絞る

隣接する話題（アプリ全体の設計論、React 一般の性能論、バリデーション UX、内部実装の解説）に広げない。
ライブラリが責任を持てない意見を公式の立場で書くことになり、読み手は必要な数行を探す羽目になる。

- 基準：その記述は「このコンポーネントが何をするか／何を指定させるか／何をしないか」に直接かかわるか。
- ただし、コンポーネントの仕様が原因で呼び出し側に義務が生じるもの（例：setValueFromEditor には任意の文字列が来るので防御的に書く、getValuesForRender は表示中セル数だけ呼ばれるので索引を作る）は範囲に入る。

## 2. 書かないと読み手が誤るか、行き詰まることだけを書く

一文ごとに読み手の注意を消費する。網羅的な表や当たり前の挙動の説明は丁寧に見えるが、大事な注意書きを埋もれさせる。

- 自然な期待どおりの挙動は書かない（例：読み取り専用セルでも選択はできる、選択範囲が自動補正される、自動スクロールする）。
- 期待から外れる挙動は書く（例：Ctrl+矢印は Excel と違い値の切れ目で止まらない、ペーストで行は増えない）。
- 短くすること自体は目的ではない。期待から外れる挙動なら長くても書く。

## 3. 構成は読み手の問いに合わせる

書き手の理解の順（仕組み → 論点 → 応用）ではなく、読み手の入口（どうやるか／なぜできないか）で組み立てる。

- 見出しを読んだだけで、読み手が自分の問いに当たる節を見つけられるようにする。
- やり方が複数あれば対等に並べ、推奨を明記する。片方を末尾の「応用」に格下げしない。
- 比較表より、読み手が陥る状況をそのまま見出しにする（例：「読み取り専用に設定していないのにセル編集できない場合」）。
- 否定（「専用の仕組みはありません」）から入らず、肯定の手順（「以下を指定すると有効になる」）から書く。
- 同じ内容を表と本文で二重に書かない。

## 4. 1つの話題の置き場所は1か所にし、他はリンクで参照する

- その機能を扱うページに書く（例：クイック編集はセル選択ページではなくセルエディタページ）。
- 他ページへの参照は `../Link` の `<Link to="...">` でクリックできるリンクにする。
- 既出の概念と同じなら、新しい規則として書かず「〜と同じ」と示す。

## 5. 注記は対象のすぐ隣に置く

散文・表・コードコメントのどれでも同じ。

- 表の特定行への注記は、その行のセルの中に書く。
- デモの操作方法はデモの前に書く（操作する前に読めるように）。
- コードコメントは、それが効く行の直上に置く。関数や型の JSDoc は名札程度にとどめる。
- 「ここから／ここまで」のマーカーは、`columnId` を含めて単位全体を囲む。

## 6. デモとの役割分担

完全な実例はデモ（ソースはページに表示される）、本文は要点。

- 本文のコード例は論点の行だけにする。ただし、その行がどこに書かれるか分かる外枠（`<EditableGrid2 columns={[{ ... }]} />` など）は残す。
- 説明は、できるだけ該当行のインラインコメントで書く。
- 論点と無関係な行はコード例から削る。
- デモにあるコードを本文に再掲しない。
- 図はコードではないので、tsx のコメントに偽装せずプレーンなコードブロックにする。

## 7. デモはそのまま真似してよい、正しく動く実物にする

読み手はデモのコードをコピーする。

- アンチパターンを体験させる切り替えなどの仕掛けを置かない。仕掛けのための分岐や引数でコードが悪くなる。
- 本文の主張どおりにデモが動くことを確かめる（例：「Delete で空になる」なら、全列の setValueFromEditor が空文字を処理すること）。
- 説明の無い不完全さを残さない（1列だけ編集できない、など）。読み手が余計な疑問を持つ。
- UI の文言は画面の利用者の言葉で書き、API 名を入れない。
- 配置は実際の画面として自然にする（送信ボタンはグリッドの下、など）。
- ※の脚注には、デモで見て試せる挙動を書く（「数字のみ貼り付け可能」など）。API 名や想像上の業務背景は書かない。
- 描画結果を確認する（ヘッダが列幅で切れていないか、など）。

## 8. 理由は正直に書き、結論は言い切る

- デモの都合による選択は、デモの都合だと書く。もっともらしい業務上の理由をこしらえると、ベストプラクティスとして真似される。
- 「〜が〜を左右する」と論点だけ示さず、「〜である必要がある」と結論を書く。

## 9. 言葉づかい

- 普通の用語を使う（「取り下げる」ではなく「クリアする」）。正確な用語を使う（「貼り付け」ではなく「クリップボード貼り付け」）。
- 前置きを書かない（「このページでは〜を説明します」「〜を目的に設計されています」）。具体的な仕組みを一文で書く。
- 太字を乱用しない。
- 「現時点で」のような、予定の無い将来をにおわせる留保を付けない。
- 読み手に検証を課さない（「〜を確認してください」）。
- 自明な前提条件を書かない。

## 10. 作業中に知っただけのことや、不確かなことは書かない

- 書き手が作業中に観察したこと（開発ビルドと本番ビルドの計測値など）や、すぐに古くなる数値は書かない。
- 「こう書かないと動かない」という回避策を書きたくなったら、ライブラリ側の問題かもしれない。ドキュメントに書く前に人間に確認する。

## 迷ったときの問い

1. これはこのコンポーネントの約束事か？
2. これが無かったら、読み手は誤るか、行き詰まるか？
3. 読み手の問いから、この場所に最短でたどり着けるか？
4. デモはそのまま真似してよく、本文の主張どおりに実際に動くか？
5. 理由は本当の理由か。結論を言い切っているか？

正しいことでも、このページの読み手に不要なら書かない。
