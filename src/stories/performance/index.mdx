# パフォーマンス

EditableGrid2 は、行数・列数が多いグリッドでも快適に編集できることを目的に設計されています。
このページでは、その仕組みと、それを活かすための実装方法を実例とともに説明します。

以下は **1万行 × 45列（45万セル）** のグリッドです。

* 12ヶ月分の月別列（計画・実績・差異）がグループ列として横方向に並びます。
* セルを編集すると、**同じ行の他の列**（差異・年間計画・年間実績・年間計画金額）へ値が波及します。
* さらに構成比・累計構成比は全行の年間計画の合計を分母に持つため、どこか1セルを編集すると**すべての行**の値が変わります。
  （構成比は1万行のうちの1セルぶんの影響なので動きがごくわずかです。他の行への波及を目で確かめるには累計構成比を見てください。）
* 上部のボタンから、**グリッドの外側**のトリガーでグリッド内の値をまとめて書き換えられます。
* 行の追加と、行頭チェックボックスによる行削除ができます。

スクロール・編集・コピー＆ペースト・一括更新のいずれも、規模にかかわらず所要時間が変わらないことを確認してください。

## 速さの前提となる2つの仕組み

### 1. 行の仮想化（グリッド側の責務）

EditableGrid2 は `@tanstack/react-virtual` による行の仮想化を内蔵しています。
`rowKeys` に1万件渡しても、実際に DOM に存在する `<tr>` は画面に見えている数十行分だけです。

表示範囲の外側をどれだけ先読みしておくかは `overscan` で調整できます（既定値は 10）。

<Source language="tsx" code={`
  <EditableGrid2
    rowKeys={rowKeys} // 1万件渡しても、DOM上の行は画面に見えている分だけ
    overscan={10}     // 表示範囲の前後に何行ぶん先読みしておくか
    {...}
  />
`} />

列の仮想化は行っていません。列数は「多くても数百」を想定しており、
上記の例のように45列であれば、横方向は DOM をすべて作っても問題にならない範囲です。

### 2. 行の値をグリッドに持たせないこと（呼び出し側の責務）

EditableGrid2 は行の値そのものを保持しません。
グリッドが受け取るのは、行の並びを表す `rowKeys` と、値を取りにいくための `getLatestRowObject` だけです。

<Source language="tsx" code={`
  <EditableGrid2
    rowKeys={rowKeys}                                  // 行の並び（行の増減・並べ替えの検知にのみ使われる）
    getLatestRowObject={index => store.getRowAt(index)} // 値は描画のたびにここから取得される
    columns={columns}
  />
`} />

この形にしておくと、**セルの値を書き換えてもグリッドの再レンダリングが発生しません**。
`rowKeys` の内容（各要素の値と並び順）が変わらない限り、グリッドは再構築されないためです。

逆に、行データを `useState` で保持して
`rows` の配列ごと作り直すような実装にすると、1セル編集するたびに1万行分の配列が作り直され、
グリッド全体が再レンダリングされます。これがもっともよくある速度低下の原因です。

<Source language="tsx" code={`
  // 避けたい実装: 1セルの編集で1万行分の配列を作り直してしまう
  const [rows, setRows] = React.useState<Row[]>(...)
  setValueFromEditor: ({ rowIndex, value }) => {
    setRows(prev => prev.map((row, i) => i === rowIndex ? { ...row, name: value } : row))
  }
`} />

## セル単位で値を購読する

行の値をグリッドの外側に置いた場合、「値が変わったことをどうやって画面に反映するか」は呼び出し側の責務になります。
ここでセル単位の購読を用意しておくと、**値が変わったセルだけ**が再レンダリングされるようになります。

上記の例では、React 標準の `useSyncExternalStore` を使っています。

<Source language="tsx" code={`
  /** ストアのセル1個分の値を購読する */
  function useCellValue<T>(store: PerfDataStore, rowId: string, field: PerfCellField, getValue: () => T): T {
    const subscribe = React.useCallback(
      onStoreChange => store.subscribeCell(rowId, field, onStoreChange),
      [store, rowId, field]
    )
    return React.useSyncExternalStore(subscribe, getValue)
  }

  // 列定義の renderBody で、そのセル自身の値だけを購読する
  renderBody: ({ row }) => (
    <SubscribedCell store={store} rowId={row.rowId} field="name" getValue={() => row.name} />
  ),
`} />

`renderBody` は React コンポーネントとして呼び出されるため、この中でフックを使えます。

<Link to="react-hook-form との統合">React Hook Form との統合</Link> における `useWatch` も、
役割としてはこれと同じです（React Hook Form 自身がセル単位の購読の仕組みを持っています）。
ただし React Hook Form は1万行規模のフィールド登録を想定していないため、
この規模では上記のような自前のストアの方が適しています。

## 値の波及（同じ行・他の行）

セル単位の購読にしておくと、「1つのセルの編集が他のセルへ波及する」計算列を素直に書けます。
波及先のセルへ変更を通知するだけで済み、グリッド全体を再描画する必要がありません。

<Source language="ts" code={`
  setPlan(rowIndex: number, month: number, value: number): void {
    const row = this.#rows[rowIndex]
    this.#grandPlanTotal += value - row.plan[month]
    row.plan[month] = value

    // 同じ行の他の列への波及
    this.#notify(row.rowId, \`plan-\${month}\`)
    this.#notify(row.rowId, \`diff-\${month}\`)
    this.#notify(row.rowId, "planTotal")
    this.#notify(row.rowId, "amount")

    // 他の行への波及（構成比の分母が変わるため、全行の構成比が変化する）
    this.#notifyAllRows("share")
  }
`} />

ここで重要なのは、**他の行への波及が1万行分のループにならない**ことです。
購読しているのは画面に表示されているセルだけなので、
論理的に1万行の値が変わっても、通知先も再レンダリングも表示中のセルの数で済みます。

## グリッドの外側からの値の変更

セルの値はグリッドの外側のストアが持っているため、グリッドの外側のボタンからも同じように書き換えられます。
グリッドに対して特別な操作は必要ありません。

<Source language="ts" code={`
  /** 全行・全ての月の実績に計画値をコピーする（12万セルの書き換え） */
  copyAllPlanToActual(): void {
    for (const row of this.#rows) {
      for (let month = 0; month < 12; month++) row.actual[month] = row.plan[month]
    }
    // 購読中（＝表示中）のセルへまとめて通知する
    this.#notifyAllSubscribedCells()
  }
`} />

なお、`renderBody` の中でストアを購読していない値
（`props.columns` の外側の state に依存した表示や、`showCheckBox` / `isReadOnly` の判定結果など）を
グリッドの外側から変えた場合は、自動的には再描画されません。
その場合は ref API の `forceUpdate()` を呼んで明示的に再描画してください。

## 行の追加・削除

行の増減は `rowKeys` の変更で表現します。
ここはグリッドの再構築が必要な操作なので、`rowKeys` を state として持ち、行の増減のときだけ更新します。

<Source language="tsx" code={`
  const [rowKeys, setRowKeys] = React.useState(() => store.getRowKeys())

  // 行追加
  const addRow = () => {
    const addedRowIndex = store.addRow()
    setRowKeys(store.getRowKeys())
    // 行数の増加がグリッドに反映された後でないと選択位置がクランプされるため、次のフレームで選択する
    requestAnimationFrame(() => gridRef.current?.selectRow(addedRowIndex, addedRowIndex))
  }

  // 行頭チェックボックスでチェックされた行の削除
  const removeCheckedRows = () => {
    const rowIndexes = (gridRef.current?.getCheckedRows() ?? []).map(({ rowIndex }) => rowIndex)
    store.removeRows(rowIndexes)
    setRowKeys(store.getRowKeys())
  }
`} />

`ref` の `selectRow()` は選択セルを変更するだけで、スクロール位置は動かしません
（選択セルへの自動スクロールは、キー操作によるセル移動のときだけ働きます）。
1万行のうちの末尾に行を追加した場合など、追加した行を画面内に入れたいときは、
スクロール位置を自分で動かす必要があります。

<Source language="tsx" code={`
  // グリッドのスクロールコンテナ（.halllky-eg2-root）を引いて末尾までスクロールする
  const scrollContainer = gridContainerRef.current?.querySelector(".halllky-eg2-root")
  scrollContainer?.scrollTo({ top: scrollContainer.scrollHeight })
`} />

`getRowKeys()` は毎回新しい配列インスタンスを返しますが、
グリッド側は配列の**内容**（各要素の値と並び順）を比較するため、
内容が同じであれば再構築は発生しません。呼び出し側で `useMemo` する必要はありません。

チェック状態は `rowKeys` の値ごとにグリッド内部で保持されるため、
行を削除しても残った行のチェック状態は維持されます。
詳しくは <Link to="選択/行選択">行選択</Link> を参照してください。

## 列定義は必ず `useMemo` で包む

`columns` の参照が変わると、表示範囲内のすべてのセルとヘッダが再レンダリングされます。
列数が多いグリッドではこの影響が大きいため、`columns` は必ず `useMemo` で参照を安定させてください。

<Source language="tsx" code={`
  // 中で参照している外側の値（ここでは store）を依存配列に含めること。
  // 含め忘れると、その値が変わっても列定義内の関数が古い値を参照したままになる。
  const columns = React.useMemo((): EditableGrid2Column<Row>[] => [...], [store])
`} />

列数が多い場合、列定義をベタ書きすると定義そのものが膨大になります。
上記の例では、月別の36列を `Array.from` によるループで生成しています。

<Source language="tsx" code={`
  const monthColumns = Array.from({ length: 12 }, (_, month) => ({
    columnId: \`month-\${month}\`,
    renderHeader: () => <HeaderText>{month + 1}月</HeaderText>,
    columns: [
      { columnId: \`plan-\${month}\`, ... },
      { columnId: \`actual-\${month}\`, ... },
      { columnId: \`diff-\${month}\`, ... },
    ],
  }))
`} />

## セルエディタの参照を安定させる

セルエディタのコンポーネントも同様です。
列定義の中でその場で生成する（例: `editor: createTextCellEditor(false)`）と、
列定義が再評価されるたびに別のコンポーネント型になり、
セルエディタが不必要に unmount / mount を繰り返します。

モジュールスコープの定数にするか、エディタ単体で `useMemo` してください。

<Source language="tsx" code={`
  // モジュールスコープの定数として参照を安定させる
  const TextEditor = createTextCellEditor(false)
`} />

## 計測について

実演画面に表示している所要時間は、
ボタンを押してからストアの書き換え・React の再レンダリング・ブラウザの描画が終わるまでの時間です
（`requestAnimationFrame` を2回挟んで計測しています）。

<Source language="tsx" code={`
  const measure = (label: string, action: () => void) => {
    const start = performance.now()
    action()
    requestAnimationFrame(() => requestAnimationFrame(() => {
      setLastOperation({ label, ms: performance.now() - start })
    }))
  }
`} />

12万セルを書き換える操作でも、実際に再レンダリングされるのは表示中の数百セルだけなので、
所要時間の大半は「ストア側のループ」であり、React の描画コストは行数に比例しません。

### 開発サーバでの計測値について

**Storybook の開発サーバ（`npm run storybook`）で表示される所要時間は、実際のアプリケーションの値より大幅に遅く出ます。**
開発時の React は本番用ビルドではなく、内部的に props の差分検査などの計測用処理が走るためです。

特に `rowKeys` が変化する操作（行の追加・削除）で差が大きく、
同じ操作・同じマシンで以下のような差がありました。

| 操作 | 開発ビルド | 本番ビルド |
| --- | --- | --- |
| 一括更新（12万セルの書き換え） | 約 26 〜 110 ms | 約 20 〜 46 ms |
| 行追加（`rowKeys` の変化） | 約 1,700 〜 2,100 ms | 約 65 〜 77 ms |
| 行削除（`rowKeys` の変化） | 約 1,900 〜 2,100 ms | 約 110 〜 136 ms |

速度を評価するときは、必ず本番ビルド（`npm run build-storybook` の出力、または実際のアプリケーション）で計測してください。
