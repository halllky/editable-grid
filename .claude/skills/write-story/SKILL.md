# ドキュメント・デモ執筆方針

## 読み手

このグリッドを使って自分の画面を作ろうとしている開発者。
「X をしたいがこのグリッドではどうやるか」「思った通りに動かないのはなぜか」という具体的な問いを持って来る。
すべての判断は「この読み手が問いの答えに最短でたどり着けるか」で行う。

## 範囲はこのコンポーネントの約束事に絞る

隣接する話題（アプリ全体の設計論、React 一般の性能論、バリデーション UX、内部実装の解説など）に広げない。
ライブラリが責任を持てない意見を公式の立場で書くことになり、読み手は必要な数行を探す羽目になる。

- 基準：その記述は「このコンポーネントが何をするか／何を指定させるか／何をしないか」に直接かかわるか。
- ただし、コンポーネントの仕様が原因で呼び出し側に義務が生じるもの（例：この関数には任意の文字列が来るので防御的に書く、この関数は表示中セル数だけ呼ばれるので索引を作る）は範囲に入る。

## 書かないと読み手が誤るか、行き詰まることだけを書く

一文ごとに読み手の注意を消費する。網羅的な表や当たり前の挙動の説明は丁寧に見えるが、大事な注意書きを埋もれさせる。

- 自然な期待どおりの挙動は書かない（例：読み取り専用セルでも選択や移動は通常どおりできる、選択中の行が消えたら選択範囲が補正される、画面外へ移動したら自動スクロールする）。
- 期待から外れる挙動は書く（例：Ctrl+矢印は Excel と違い値の切れ目で止まらない、ペーストで行は増えない）。
- 短くすること自体は目的ではない。期待から外れる挙動なら長くても書く。

## 構成は読み手の問いに合わせる

書き手の理解の順（仕組み → 論点 → 応用）ではなく、読み手の入口（どうやるか／なぜできないか）で組み立てる。

- 読み手はサイトのメニューのページ名を他のページ名と見比べて、このページを選んで来る。その時点で生じている『このページにはこういう内容があるはず』という期待に応えるように書くこと。
- 見出しを読んだだけで、読み手が自分の問いに当たる節を見つけられるようにする。
- 自然に実装すると陥りがちな不具合への対策を書くセクションは、その不具合の状況をそのまま見出しにする。

## 1つの話題の置き場所は1か所にし、他はリンクで参照する

具体的情報があちこちに書かれるとメンテナンス性が下がるため。

- 例えば「セル選択」のページで「クイック編集」機能への言及が必要になったとして、セル選択のページにクイック編集の詳細を書いてはいけない。以下いずれかで回避する。
  - クイック編集側の仕様が変わったときにセル選択側を書き換えなくてよいように、セル選択側で言いたい内容を損なわない範囲で、抽象的に言い換える。
  - セル選択側には必要な最低限の具体的情報だけ書き、クイック編集の詳細が書いてあるページにリンクする。
- 他ページへの参照は `../Link` の `<Link to="...">` でクリックできるリンクにする。to には遷移先の stories.tsx の title（例："編集/セルエディタ"）を渡す。

## 説明文とデモとの役割分担

完全な実例はデモ（ソースはページに表示される）、本文は仕様やルールなど要点。

- 本文のコード例は論点の行だけにする。ただし、その行がどこに書かれるか分かる外枠（`<EditableGrid columns={[{ ... }]} />` など）は残す。
- 論点と無関係な行はコード例から削る。

## デモはそのまま真似してよい、正しく動く実物にする

読み手はデモのコードをコピーする。

- アンチパターンは原則書かない。書かざるを得ない場合はコメントで注意を補足する。
- デモの都合による選択は、デモの都合だと書く。もっともらしい業務上の理由をこしらえると、ベストプラクティスとして真似される。
- 本文の記述とデモの挙動で矛盾があってはならない。
- UI の文言は画面の利用者の言葉で書く。
- ※の脚注には、デモのその項目で何を示したいのかを書く。
- 描画結果を確認する（ヘッダが列幅で切れていないか、など）。

## AI特有の癖・傾向の排除

- 太字を乱用しない。
- 見ればわかる前提は書かない。
  - 利用者は画面を見る。mdxのテキストで書かれていなくても、テキストの大きさや距離といったレイアウト、メニュー構成から見たそのページのサイト全体における位置づけ、デモコンポーネントを見れば言いたいことが一目瞭然である情報などはある。
- 作業中に知っただけのことや、不確かなことは書かない
  - 書き手が作業中に観察したこと（開発ビルドと本番ビルドの計測値など）や、すぐに古くなる数値は書かない。書き手（AI）が作業中に得た文脈ではなく、ドキュメントの読み手が持っている情報を前提に書く。

## 迷ったときの問い

1. これはこのコンポーネントの約束事か？
2. これが無かったら、読み手は誤るか、行き詰まるか？
3. 読み手の問いから、この場所に最短でたどり着けるか？
4. デモは本文の主張どおりに実際に動くか？

正しいことでも、このページの読み手に不要なら書かない。
